# Running HATCHet as an MCP server

An MCP (Model Context Protocol) server exposes HATCHet's pipeline stages as tools an AI
coding agent can call directly, so a user can run an analysis by describing it in plain
language instead of writing a `config.yaml` and invoking Snakemake.

The server is generated from `notebooks/hatchet_cnv_workflow.ipynb` by
[Paper2Agent](https://github.com/jmiao24/Paper2Agent): one tool per notebook section.

> [!IMPORTANT]
> `notebooks/` is currently listed in `.gitignore`, so the source notebook is not part of
> the repository. Generating the server therefore requires a local checkout rather than a
> clone, and the `reference` URL embedded in each tool does not resolve. Un-ignore
> `notebooks/` to make the tutorial distributable.

> [!NOTE]
> This is for interactive, single-patient exploration and interpretation. Cohort
> production runs still belong in the Snakemake workflow, which has a DAG, resumability,
> per-rule logs and benchmarks, and cluster submission. The MCP tools have none of those
> and re-run on every call.

## Tools

| Tool | Stage | Key inputs |
|---|---|---|
| `hatchet_check_installation` | `check` | none; optional `solver` |
| `hatchet_cluster_bins` | `cluster-bins` | `bb_dir`, `genome_size`, `region_bed` |
| `hatchet_review_cluster_model_selection` | - | `bbc_dir` |
| `hatchet_compute_cn` | `compute-cn` | `bbc_path`, `seg_path`, `genome_size`, `region_bed` |
| `hatchet_plot_cn_profiles` | `plot-cn` | `result_dir`, `genome_size`, `region_bed` |
| `hatchet_plot_cn_panel` | `plot-panel` | `panel_entries`, `genome_size`, `region_bed` |

Each tool returns `{message, reference, artifacts}`, where every `artifacts[].path` is
absolute. That is what lets the agent chain one stage into the next without being told
filenames, and lets it read the result tables afterwards to answer questions.

## Prerequisites

A conda environment with HATCHet installed, including the compiled `_hmm_cpp` extension
and an ILP solver. `compute-cn` requires a Pyomo-supported solver in every mode, `cd`
included, so a pip-only environment is not sufficient.

```sh
mamba env create -f environment.yaml -p /path/to/hatchet-env
CONDA_PREFIX=/path/to/hatchet-env /path/to/hatchet-env/bin/python -m pip install \
  --no-build-isolation -e .
/path/to/hatchet-env/bin/python -m pip install fastmcp
```

There is no need to verify the environment by hand. `hatchet_check_installation` wraps the
`hatchet check` subcommand: it simulates an input cohort, runs cluster-bins, compute-cn and
plot-cn end to end against known ground truth, and reports per-assertion PASS/FAIL along
with the solver it resolved. Ask the agent to run it, or invoke the CLI directly:

```sh
/path/to/hatchet-env/bin/hatchet check
```

The tool auto-detects gurobi then cbc when `solver` is left unset, so a licensed Gurobi is
picked up automatically and cbc is used otherwise.

## Step 1: register the server

Registration records *how to launch* the server; nothing starts yet. The server uses the
stdio transport, so the client spawns it as a child process per session and speaks
JSON-RPC over its stdin and stdout.

```sh
claude mcp add hatchet3 -s user \
  -e HATCHET_CNV_WORKFLOW_OUTPUT_DIR=/path/to/outputs \
  -- /path/to/hatchet-env/bin/python /path/to/src/<repo_name>_mcp.py
```

| Argument | Meaning |
|---|---|
| `hatchet3` | Server name shown by `claude mcp list` and `/mcp` |
| `-s user` | Scope. See the table below; the default is `local` |
| `-e KEY=VALUE` | Environment variables passed to the server process |
| `--` | End of options; everything after is the launch command |

`HATCHET_CNV_WORKFLOW_OUTPUT_DIR` sets where tools write results. Without it they default
to a `tmp/outputs` directory beside the server source, which is rarely where you want
them. `HATCHET_CNV_WORKFLOW_INPUT_DIR` behaves the same way for inputs.

Filled in, the whole registration is one line:

```sh
claude mcp add hatchet3 -s user -e HATCHET_CNV_WORKFLOW_OUTPUT_DIR="$HOME/hatchet-runs" -- "$HOME/envs/hatchet-env/bin/python" "$HOME/HATCHet_Agent/src/hatchet-long-read_mcp.py"
```

Invoking the environment's interpreter directly, rather than through a `uv run` wrapper,
keeps startup fast and removes `uv` as a runtime dependency of every session.

Confirm the entry and its resolved settings with:

```sh
claude mcp get hatchet3
```

### Scopes

| Scope | Stored in | Visible to |
|---|---|---|
| `local` (default) | `~/.claude.json`, keyed to a project root | You, within that project only |
| `user` | `~/.claude.json`, global | You, everywhere |
| `project` | `.mcp.json` at the repo root, committed | Anyone who clones the repo |

Use `user` for a personal install.

> [!IMPORTANT]
> `local` scope keys on the enclosing **git root**, not the current directory. Registering
> from a subdirectory covers the whole repository, and registering from a directory that is
> not itself a repository attaches the server to whichever repository contains it. A server
> installed from inside a generated project folder therefore lands on the parent checkout
> rather than anywhere useful, and is invisible from every other project.

### Alternative: `fastmcp install`

Paper2Agent documents this route instead. Run it from the project you want the server
available in; it registers at `local` scope against that project's git root.

```sh
cd /path/to/your/analysis/project
fastmcp install claude-code /path/to/src/<repo_name>_mcp.py --python /path/to/hatchet-env/bin/python --name hatchet3 --env HATCHET_CNV_WORKFLOW_OUTPUT_DIR=/path/to/outputs
```

The generated launcher wraps the server in `uv run --with fastmcp fastmcp run`, so `uv`
must be on `PATH` for every session, not just at install time.

### Alternative: a committed `.mcp.json`

`.mcp.json` is the standard project-scope config file. Collaborators who clone the repo
are offered the server after a one-time approval prompt.

```json
{
  "mcpServers": {
    "hatchet3": {
      "command": "/path/to/hatchet-env/bin/python",
      "args": ["/path/to/src/<repo_name>_mcp.py"],
      "env": { "HATCHET_CNV_WORKFLOW_OUTPUT_DIR": "/path/to/outputs" }
    }
  }
}
```

> [!WARNING]
> Absolute interpreter and source paths are machine-specific, so a committed `.mcp.json`
> only helps collaborators whose layout matches. Hosting the server over HTTP and
> registering it by URL (`claude mcp add --transport http <name> <url>`) is the portable
> option.

## Step 2: verify the connection

This launches each registered server and performs the MCP `initialize` handshake, so it
is a real health check rather than a config dump.

```sh
claude mcp list
```

Look for `hatchet3: ... - OK Connected`. A failure here is almost always a wrong
interpreter path or a missing executable in `PATH`.

## Step 3: start a session

```sh
cd /path/to/analysis/directory && claude
```

The working directory determines which `local`-scope servers load, and anchors the
relative paths the agent uses when it reads result tables or writes summaries.

## Step 4: describe the analysis

Give the three input paths and the question. The agent selects tools, chains their
artifact paths, and reads the resulting tables to answer follow-ups.

```
Use the HATCHet MCP. First check the installation is working, then analyse this sample.

bb_dir:      <path to a bb_dir>
genome_size: data/reference/hg38.chrom.sizes
region_bed:  data/reference/hg38.regions.bed

Run cluster-bins, then compute-cn testing both the diploid and tetraploid hypotheses.
Report the inferred purity and clone proportions per sample, whether a whole-genome
duplication was selected, and how many clones won. Then plot the copy-number profiles.
```

Useful follow-ups once a solution exists:

- Which chromosome arms are LOH in the tumor clones?
- List every segment where the clones differ, longest first.
- Do the tumor samples share clones at different proportions?
- Re-run forcing diploid only and tell me how much worse the fit is.

## Choosing the reference files

`genome_size` is a two-column chromosome sizes file. `region_bed` must have **exactly four
columns** (`#CHR`, `START`, `END`, `NAME`); `io_utils.read_region_bed` names four columns
with no header, so a file with more columns is silently misparsed into the index rather
than rejected. The pipeline's own `aux/segment.bed` carries a fifth column and is
therefore not a valid `region_bed`. Use the four-column files under `data/reference/`.

Pick the build matching the bins: every bin coordinate must fall inside the chromosome
sizes file.

## Notes

- Tools default to `force=True` and recompute on every call. Point the plotting tools at
  an existing `result_dir` when you only want new figures.
- Runtime scales with the number of bins, the number of tumor samples, the width of the
  `minK`-`maxK` sweep, and `restarts`. Narrow the sweep for a first pass.
- The server imports `hatchet` from whichever checkout its environment was installed
  against. Install with `-e` to track a working tree.
